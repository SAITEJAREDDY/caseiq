# CaseIQ data

This directory holds **two separate, unrelated-in-scale datasets**:

1. **The live-app dataset** (`raw/`) — small, hand-sized for the Streamlit
   demo. `app.py` and `agent/neo4j_loader.py` read this one today.
2. **The CaseIQ synthetic-data program** (`raw_v2/` + `phase2/` + `phase3/`)
   — a much larger, three-phase dataset built for offline research,
   evaluation, and future agentic-eval work. **Nothing in the live app reads
   this yet.**

If you're looking for what powers the running demo, see the root
[`README.md`](../README.md). This file is exclusively about the data.

---

## 1. Live-app dataset — `raw/` (Phase 0)

Generated by `generate_data.py` (`python3 data/generate_data.py`),
`random.seed(42)`, no LLM calls. 2,000 customers · 10,000 cases · 50 products
· 500 KB articles · 150 agents · 40 skills · ~35,000+ relationship edges,
across 14 CSVs. This is what `agent/neo4j_loader.py` loads into Neo4j
AuraDB and what the running Streamlit app actually queries. Gitignored;
regenerate anytime with the command above (idempotent, same seed every time).

---

## 2. The synthetic-data program — `raw_v2/` + `phase2/` + `phase3/`

A three-phase, 25,000-case dataset (~2M rows total: ~395K in Phase 1, ~531K
in Phase 2, ~1.06M in Phase 3) built to support offline model evaluation,
routing/diagnosis research, and (eventually) agentic-trace evaluation — well
beyond what the live demo needs. Each phase answers a different question
about the same 25,000 cases and is generated by its own package under
`generators*/`:

```
generators/            -> raw_v2/    (Phase 1: WHAT happened)
generators_phase2/     -> phase2/    (Phase 2: WHAT evidence existed)
generators_phase3/     -> phase3/    (Phase 3: WHAT investigators did)
```

**Phases are additive and strictly frozen once built.** Phase 2 only reads
`raw_v2/` (read-only); Phase 3 only reads `raw_v2/` and `phase2/` (read-only).
Nothing downstream ever regenerates or edits an upstream phase. Every phase's
`validate_*.py` re-checks a SHA-256 checksum manifest of every upstream file
on every run, so any accidental mutation is caught immediately, not
discovered later.

All three phases join on the same case ids (`CS00001`...`CS25000`) plus
shared reference ids (customers, products, components, agents, teams, KB
articles) — there is no new customer/product/agent/team entity introduced
past Phase 1, only new *facts about* the existing ones.

### Phase 1 — `raw_v2/` — the support-domain foundation

**What actually happened to each case.** Full taxonomy (18 issue categories,
126 subcategories, 40 root causes, 42 resolution types, 250 components across
50 products, 24 teams, 85 skills, 965 KB articles) plus, per case, both an
**observable** view (`case_observable.csv` — what a customer/agent would see:
title, description, reported impact, priority) and a **hidden ground-truth**
view (`case_ground_truth.csv` — true product/component/root cause/resolution/
severity/difficulty archetype). 45 CSVs total.

- Build: `python3 data/generators/build_dataset.py`
- Validate: `python3 data/generators/validate.py`
- Full schema: [`raw_v2/DATA_DICTIONARY.md`](raw_v2/DATA_DICTIONARY.md)
- Deterministic (`random.seed(42)`), except case/KB-article narrative text,
  which is LLM-written (Together AI, `Qwen/Qwen3.8-Flash`) and disk-cached.
- **Status: frozen.** Do not regenerate, modify, or rebalance.

### Phase 2 — `phase2/` — diagnostic & operational intelligence

**What technical evidence existed around each case.** Telemetry, discrete
signals, change/deployment history, a component dependency graph, platform
incidents, and SLA/capacity context — ~505,500 rows across 22 CSVs. Every
evidence table is fully observable (no causal labels); all causal judgments
(which change/signal actually caused the case, evidence sufficiency, expected
confidence) live only in `phase2_ground_truth.csv`. The central mechanism:
every piece of evidence is generated by looking up the case's *existing*
Phase 1 root cause in a hand-authored pattern table
(`evidence_taxonomy.ROOT_CAUSE_EVIDENCE_PATTERNS`), never invented
independently and reconciled afterward.

- Build: `python3 data/generators_phase2/build_phase2.py --full`
  (`--skip-narratives` to skip the LLM pass)
- Validate: `python3 data/generators_phase2/validate_phase2.py`
- Full schema: [`phase2/DATA_DICTIONARY.md`](phase2/DATA_DICTIONARY.md)
- Own seed (`PHASE2_SEED = 2026`), independent of Phase 1's `random.seed(42)`.
- **Status: frozen.** Do not regenerate, modify, or rebalance.

### Phase 3 — `phase3/` — investigation, decisions, and resolution lifecycle

**What support engineers actually did** while investigating and resolving
each case: triage, routing, diagnostic hypotheses and the evidence queries
that update them, resolution attempts, escalations, KB/similar-case usage,
collaboration, verification, closure, and reopens — ~1,060,800 rows across 21
CSVs. Modeled as a forward time-simulation per case: a hypothesis at 09:10
cannot know what a query at 09:42 will reveal (enforced and validated — no
Phase 2 row is ever referenced before its own timestamp). Every branch is
derived from existing Phase 1/2 fields (symptom-to-subcategory weights,
team-ownership tables, root-cause-to-resolution weights, Phase 1's own
`similar_cases.csv`) rather than invented independently, and the investigation
is always forced to converge on Phase 1's actual root cause/resolution for
every non-open case — what varies by difficulty is the *path*, not the
destination.

- Build: `python3 data/generators_phase3/build_phase3.py --full`
  (`--skip-narratives` to skip the LLM pass)
- Validate: `python3 data/generators_phase3/validate_phase3.py`
- Full schema: [`phase3/DATA_DICTIONARY.md`](phase3/DATA_DICTIONARY.md)
- Own seed (`PHASE3_SEED = 2027`). No wall-clock anchoring anywhere — every
  timestamp is an offset from a case's own `created_date`/
  `gt_resolution_duration_hours`, so (unlike an earlier version of Phase 2)
  there's no `datetime.now()`-shaped reproducibility risk to guard against.
- **Status: frozen.** Do not regenerate, modify, or rebalance.

### Reproducibility, shared across Phase 1-3

Each phase uses its own explicit `random.Random` seed, threaded as a function
argument through every generator (never touching another phase's RNG state).
Re-running any phase's build script with unchanged upstream input reproduces
byte-identical structural output — verified for each phase by running its
full build twice and diffing every CSV. The only intentionally-non-mechanical
content is a small set of LLM-written narrative fields (case/KB text in
Phase 1; incident/deployment text in Phase 2; escalation/engineering-finding
text in Phase 3) — everything else (IDs, timestamps, causal links, ordering)
is deterministic Python. LLM calls go through
`data/generators/llm_client.py` (Together AI, `Qwen/Qwen3.8-Flash`), shared
by all three phases, with a disk cache (`data/generators/.narrative_cache/`)
keyed by exact request hash so a re-run replays cached text instead of
re-spending tokens.

### Phase 4 — the Neo4j runtime graph (built from this data, not stored in `data/`)

Phase 4 transforms the **observable** slice of Phases 1-3 into a queryable
Neo4j graph — a separate AuraDB instance from the live app's, loaded by
`agent/graph_v2/build_graph.py`. Every hidden/ground-truth field is
deliberately excluded from that graph and lives only in `data/eval/
eval_store.py`, a read-only accessor over the same `*_ground_truth.csv` /
`phase3_event_quality_labels.csv` / `ideal_investigation_requirements.csv`
files described above. See `docs/GRAPH_SCHEMA.md`,
`docs/GRAPH_DATA_BOUNDARIES.md`, and `docs/GRAPH_QUERY_CATALOG.md` at the
repo root for the full schema, the observable/hidden boundary reasoning, and
the canonical query catalog.

### Phase 5 — the baseline diagnostic agent (also not stored in `data/`, except its run outputs)

Phase 5 (`agent/agent_v2/`) is the first thing that actually *uses* the
Phase 4 graph: a real LLM agent that investigates a case through a curated,
read-only, time-gated 14-tool layer, maintains explicit hypothesis state,
and produces a structured, evidence-cited diagnosis — with the same zero
access to `data/eval/eval_store.py` that Phase 4 established. Its
experiment outputs (one JSON per investigation run, plus an index) land in
`data/agent_runs/` — the only Phase 5 artifact that lives under `data/`,
and it is an experimental output, not synthetic source truth, never read
back into the runtime path. See `docs/AGENT_TOOL_CATALOG.md`,
`docs/BASELINE_AGENT_ARCHITECTURE.md`, `docs/AGENT_DATA_BOUNDARIES.md`, and
`docs/AGENT_EXPERIMENTS.md` at the repo root.

### Phase 6 — the deterministic evaluation harness (also not stored in `data/`, except its splits/experiment outputs)

Phase 6 (`agent/eval_v2/`) is the first thing that grades Phase 5's agent:
a deterministic scorer (no LLM judge, no Jev) that compares stored
`data/agent_runs/*.json` runs against the same hidden ground truth Phase 4
excludes from the graph (`data/eval/eval_store.py`, extended with two new
read-only accessors for team ownership and incident relationship — no
existing accessor changed). Its own artifacts:
`data/eval/splits/` (the locked dev/40% · validation/30% · test/30% case-ID
partition over the Phase 4 graph's 2,500 cases) and `data/experiments/`
(one folder per experiment: case-level metrics, confusion matrices, and a
Markdown report — never overwritten, per-experiment). Neither
`agent/agent_v2/` nor the live app reads anything under
`data/experiments/`; the boundary is checked mechanically by
`agent/eval_v2/validate_boundaries.py`. See `docs/EVALUATION_ARCHITECTURE.md`,
`docs/EVALUATION_METRICS.md`, `docs/EVALUATION_SPLITS.md`, and
`docs/EVALUATION_EXPERIMENTS.md` at the repo root — the last of these
documents an important, honest early finding: across every run scored so
far, the baseline agent never once populated an ID-valued prediction field
(product/component/category/root-cause/causal-change/severity/team all
stayed `null`), which is reported, not yet acted on.

### Phase 7 — Jev primitive evaluation (also not stored in `data/`, except its frozen config, analyses and experiment outputs)

Phase 7 (`agent/jev_v2/`) asks a narrower question than Phase 5/6: given the
same observable case snapshot, how well can **Jev** (a typed, probabilistic
decision model) make one individual decision at a time? It is offline only —
nothing is wired into the agent. Six decisions (issue category, root cause,
causal change, owning team, evidence sufficiency, incident relationship) are
each posed as one question over a fixed candidate set, scored against the same
hidden truth as Phase 6 (only `agent/jev_v2/scoring.py` reads it), and compared
with an LLM baseline on identical inputs. It reuses Phase 6's dev/validation/
test splits and its experiment registry: Phase 7 experiments are folders in
`data/experiments/` tagged `jev_primitive` or `llm_primitive_baseline`, with a
`decisions.jsonl` of raw responses instead of per-case agent metrics.
`data/eval/jev/` holds the Stage B frozen configuration
(`stage_b_frozen_v1.json` plus a hash manifest), the sealed locked-benchmark
configuration (`locked_benchmark_frozen_v1.json` plus its manifest, recorded as
superseded before use in `locked_benchmark_frozen_v1_superseded.json`; the locked
run's one-shot marker `locked_benchmark_run_state.json` appears only once that
run starts), offline candidate and Stage C review analyses, and crash-safe run
checkpoints. Jev is reached through a dependency-free direct HTTP
client; installing the official `typesafe-sdk` is unsafe here (it upgrades
`tenacity` past the `<9` pin `langchain` and `streamlit` need). See
`docs/JEV_*.md` at the repo root; `docs/JEV_ISSUE_LOG.md` records the issues
found and what remains open.

### Phase 8 — Jev agent-trace evaluation (code in `agent/trace_eval_v2/`; artifacts under `data/eval/trace_eval/`)

Phase 8 evaluates completed Phase 5 traces with six narrow typed judgments (support, missed evidence, distractor anchoring, premature close, final consistency,
human review), answered by Jev and by an LLM judge on the identical packet and scored against deterministic reference labels that live in evaluation-only code.
`data/eval/trace_eval/` holds the 300-trace dev pool, the 150-trace corpus, the review context, the reference labels and the analysis output; the registered
experiments are folders in `data/experiments/` tagged `trace_eval_jev` / `trace_eval_llm`. See `docs/PHASE8_TRACE_EVALUATION.md` and `docs/TRACE_EVAL_*.md`. Closed.

### Phase 9A — the contract-hardened agent (code in `agent/agent_v3/`)

The same model as Phase 5, made to obey its tool, evidence and final-answer contract. Its artifacts: `data/agent_runs_v3/` (one JSON per run plus `runs_index.jsonl`, tagged
`iter50_a` = first version, `iter50_b` = after the one correction, `verify100_final` = the 100-case verification, stopped at 72 cases; `data/agent_runs_v3_smoke/` holds two
provider-compatibility smoke runs) and `data/eval/agent_contract_9a/` (the two disjoint dev cohorts `cohort_iter50_v1.json` and `cohort_verify100_v1.json`, `frozen_inputs_9a.json`
= sha256 pins of the Phase 1-8 files taken before the first live run, the Phase 9 smoke set, per-run batch logs and `reports/`). The machine-readable contract is
`agent/contracts/agent_contract_v1.json`. Runs keep the Phase 5 record shape, so the unchanged Phase 6 evaluator can score them.

### Phase 9 — the runtime verifier (code in `agent/runtime_verifier/`; UI in `pages/1_Diagnostic_Agent.py`)

Deterministic checks plus three Jev signals plus a policy that ACCEPTs, asks for one more investigation round, or routes to human review. Its artifacts are
`data/runtime_verifier_runs/` (one JSON per verified run — the agent run, every verification pass, the decision, the review packet when there is one — plus `index.jsonl`).
See `docs/PHASE9_RUNTIME_VERIFIER.md`.

### What's not built or not done

- The Phase 7 locked benchmark was never run (its freeze is recorded as superseded); the locked test split has not been used by any evaluation, and the validation split was used only by Phase 7 Stage C and its opaque-key control.
- Phase 9A's 100-case verification stopped at 72 of 100 cases and has no write-up of its own (the README and the contract JSON describe it).
- No integrated comparison of a stronger agent model yet; the current agent is weak (Phase 6 judges 3 of the 72 verification cases correct) and abstains often.
- The runtime verifier's thresholds are hand-set defaults and were smoke-tested on 16 dev cases only.

## Directory map

```
data/
├── generate_data.py          # Phase 0 generator (live-app dataset)
├── raw/                       # Phase 0 output — gitignored, live app reads this
├── generators/                 # Phase 1 generator package
├── raw_v2/                     # Phase 1 output + DATA_DICTIONARY.md
├── generators_phase2/          # Phase 2 generator package
├── phase2/                     # Phase 2 output + DATA_DICTIONARY.md
├── generators_phase3/          # Phase 3 generator package
├── phase3/                     # Phase 3 output + DATA_DICTIONARY.md
├── eval/                       # read-only hidden-ground-truth accessor (eval_store.py) and every evaluation artifact
│   ├── splits/                  # Phase 6 locked dev/validation/test case-ID assignment
│   ├── jev/                     # Phase 7 frozen Stage B config + manifest, candidate analyses, run checkpoints
│   ├── trace_eval/              # Phase 8 trace pool, corpus, review context, reference labels, analysis output
│   └── agent_contract_9a/       # Phase 9A cohorts, frozen-input pins, Phase 9 smoke set, batch logs, reports/
├── agent_runs/                 # Phase 5 run output — one JSON per agent run + runs_index.jsonl (never written after Phase 5)
├── agent_runs_v3/              # Phase 9A agent run output (tags iter50_a, iter50_b, verify100_final, ui)
├── agent_runs_v3_smoke/        # two provider-compatibility smoke runs (not part of any cohort)
├── runtime_verifier_runs/      # Phase 9 verified runs + index.jsonl
├── comparison_runs/            # LLM Only runs for the architecture comparison (the other two architectures reuse agent_runs_v3 and runtime_verifier_runs)
├── early_triage_eval/          # Jev early-triage dev comparison: cases_v1.json (fixed list), runs/ (one record per case), report_v1.{json,md}
├── experiments/                 # Phase 6-8 experiment output — one folder per experiment + registry.jsonl
└── eval_runs/                  # Logged LangSmith eval-run JSON snapshots (live app, unrelated to Phase 6)
```

Code and docs for Phases 4-9 live at the repo root, not under `data/`: `agent/graph_v2/` (Phase 4), `agent/agent_v2/` (5), `agent/eval_v2/` (6), `agent/jev_v2/` (7),
`agent/trace_eval_v2/` (8), `agent/agent_v3/` (9A), `agent/runtime_verifier/` (9), and `docs/` — see the root `README.md`.
