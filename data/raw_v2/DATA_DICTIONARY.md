# CaseIQ Phase 1 — Support Domain Foundation Dataset

Data dictionary for `data/raw_v2/`. This dataset is additive to, and does not
replace, the original Phase 0 dataset in `data/raw/` — the live app and
`agent/neo4j_loader.py` still run against `data/raw/` until a later phase
wires this dataset in.

Generated by `data/generators/build_dataset.py`. Ontology tables are
hand-authored, deterministic Python (`data/generators/taxonomy.py`,
`random.seed(42)`) — no LLM involvement. Case ground truth
(`data/generators/generate_cases.py`) is also fully deterministic. The **only**
LLM-generated content is case `title`/`description` text and KB article
`title`/`content_summary`/`content_body` text, produced by Together AI
(`Qwen/Qwen3.8-Flash`, `reasoning_effort: "low"`) in `narratives.py`, cached to
`data/generators/.narrative_cache/` for reproducibility/resumability.

## Section 1 — Observable vs. Ground Truth (read this first)

This is the most important structural decision in the dataset. **`cases.csv`**
contains both layers in one row, distinguished by column naming:

- **Observable columns** (unprefixed): what a system could realistically know
  the moment the case is filed — `title`, `description`, `customer_id`,
  `product_reported_id`, `environment`, `region`, `reported_business_impact`,
  `reported_affected_users`, `priority`, `status`, `created_date`.
- **Ground-truth columns** (prefixed `gt_`): what was only known after
  investigation/resolution — `gt_product_id`, `gt_component_id`,
  `gt_issue_category_id`, `gt_issue_subcategory_id`, `gt_root_cause_id`,
  `gt_resolution_type_id`, `gt_primary_team_id`, `gt_secondary_team_id`,
  `gt_severity`, `gt_true_business_impact`, `gt_true_affected_users`,
  `gt_resolution_duration_hours`, `gt_resolved_date`, `gt_escalated`,
  `gt_reopened`, `gt_csat_score`, `gt_assigned_agent_id`,
  `gt_difficulty_archetype`.

Two convenience exports enforce this split structurally so a classifier can't
accidentally train on leaked labels:

- **`case_observable.csv`** — `id` + every observable column only.
- **`case_ground_truth.csv`** — `id` + every `gt_` column only.

**A model being built/evaluated in Phase 2+ should only ever read from
`case_observable.csv`** (or the observable columns of `cases.csv`) as input,
and only compare its predictions against `case_ground_truth.csv`.

Two fields deliberately let the observable and ground-truth layers diverge,
by design, to model real intake uncertainty:

- `product_reported_id` (observable, what the customer says) vs.
  `gt_product_id` (ground truth) — these differ for the
  `wrong_product_mentioned` difficulty archetype (~7% of cases).
- `reported_business_impact` / `reported_affected_users` (observable, what
  the customer estimated) vs. `gt_true_business_impact` /
  `gt_true_affected_users` (ground truth, confirmed scope) — these differ
  whenever the customer's initial estimate turned out to be off (a random
  0.5x–1.5x noise factor is applied on every case, so this is a graded
  divergence, not just an archetype flag).

`gt_severity` is derived from `gt_true_business_impact` + noise — **never**
from customer tier. `validate.py` explicitly checks this (severity
distributions are compared across gold/silver/bronze tiers and must not
collapse to a single value per tier).

## Section 3 — Relationship / weight tables

Weight columns use a 1–3 scale (3 = strong/typical association, 1 =
weak/occasional) except where noted. These encode the *possibility space* the
deterministic case generator samples from — they are not per-case facts.

| File | Columns | Meaning |
|---|---|---|
| `product_components.csv` | `product_id, component_id` | Which components exist on which products (many-to-many; every component belongs to ≥1 product) |
| `product_teams.csv` | `product_id, team_id, role, weight` | Team(s) that own a product line; `role` = primary/secondary |
| `component_teams.csv` | `component_id, team_id, role, weight` | Team(s) most associated with a specific component, derived from the component's issue-category tags |
| `issue_subcategory_symptoms.csv` | `subcategory_id, symptom_id, weight` | Which symptoms plausibly present for a subcategory (4–6 per subcategory) |
| `issue_subcategory_components.csv` | `subcategory_id, component_id, weight` | Which components are plausibly implicated by a subcategory |
| `issue_subcategory_skills.csv` | `subcategory_id, skill_id, weight` | Skills normally needed to investigate a subcategory (2–3 per subcategory) |
| `issue_subcategory_teams.csv` | `subcategory_id, team_id, role, weight` | Owning team(s) for a subcategory — **every subcategory has ≥2 teams listed**, and many have close weights, modeling genuine routing ambiguity (e.g. Performance/Latency spreads across Application Platform, SRE, Database, Networking, and Third-Party Vendor teams) |
| `issue_subcategory_root_causes.csv` | `subcategory_id, root_cause_id, weight` | Plausible root causes for a subcategory (2–4 per subcategory — never a deterministic 1:1) |
| `root_cause_resolutions.csv` | `root_cause_id, resolution_type_id, weight` | Plausible resolution types for a confirmed root cause (1–4 per root cause) |
| `agent_skills.csv` | `agent_id, skill_id, proficiency` | `proficiency` = basic/intermediate/expert |
| `agent_products.csv` / `agent_components.csv` | `agent_id, product_id` / `agent_id, component_id` | Agent's product/component expertise |
| `agent_teams.csv` | `agent_id, team_id` | Agent's primary team (redundant with `agents.primary_team_id`, provided as an explicit edge for graph traversal) |
| `agent_issue_category_experience.csv` | `agent_id, category_id, case_count` | How many historical cases (this dataset) that agent has handled per issue category |
| `customer_cases.csv` | `customer_id, case_id` | Who filed the case |
| `case_products.csv` | `case_id, product_id, relation` | `relation` = `reported` (observable, `product_reported_id`) or `confirmed` (ground truth, `gt_product_id`) — both rows always present, identical unless `wrong_product_mentioned` archetype |
| `case_components.csv` | `case_id, component_id, relation` | `relation` = `confirmed` (the true component) or `candidate` (a second, plausible-but-wrong component, present only for `multi_component_symptoms` archetype cases) |
| `case_symptoms.csv` | `case_id, symptom_id` | The 1–3 symptoms actually present on the case (ground truth; also what the narrative describes) |
| `case_required_skills.csv` | `case_id, skill_id` | Ground-truth skills actually needed to resolve the case |
| `case_team_ownership.csv` | `case_id, team_id, role` | Ground-truth owning team(s); `role` = primary/secondary |
| `agent_cases.csv` | `agent_id, case_id, role` | `role` = assigned (open case) / resolved / resolved_escalated |
| `similar_cases.csv` | `case_id_a, case_id_b, similarity_score` | Pairs grouped by shared `gt_issue_subcategory_id` — **two similar-symptom cases can and do have different confirmed root causes**, since similarity is symptom/subcategory-based, not root-cause-based |
| `case_articles.csv` | `case_id, article_id` | KB articles referenced while resolving a case (only for resolved/escalated cases, ~85% coverage) |
| `article_products.csv`, `article_components.csv`, `article_issue_categories.csv`, `article_issue_subcategories.csv`, `article_symptoms.csv`, `article_root_causes.csv`, `article_resolutions.csv` | `article_id, <entity>_id` | What a KB article covers. "Specific" articles link to 1 subcategory + a few symptoms/root causes; "broad" articles link to up to 3 subcategories and a wider symptom/root-cause spread |

## Section 5 — The 18 issue categories

`IDENTITY_AUTH` (Identity/Authentication), `AUTHZ` (Authorization/Permissions),
`NETWORKING`, `PERFORMANCE` (Performance/Latency), `RELIABILITY`
(Reliability/Availability), `DEPLOYMENT` (Deployment/Upgrade),
`CONFIGURATION`, `DATA_CORRUPTION` (Data/Corruption), `INTEGRATION_API`
(Integration/API), `PROVISIONING` (Provisioning/Onboarding), `SECURITY`,
`COMPLIANCE`, `BILLING` (Billing/Commerce), `UX_DEFECT` (User
Experience/Functional Defect), `STORAGE_DB` (Storage/Database), `CAPACITY`
(Capacity/Scaling), `THIRD_PARTY` (Third-Party/Dependency), `UNKNOWN`
(Unknown/Other). The keys shown are internal identifiers used in
`data/generators/taxonomy.py`; `issue_categories.csv` stores the IC0# id and
display name.

`CAPACITY` and `THIRD_PARTY` were added beyond the 16 categories the Phase 1
spec named explicitly, so that "dependency failure" and "capacity
limitation"-flavored root causes have a natural home — this matters for the
`dependency_root_cause` difficulty archetype (Section 6).

## Section 6 — Intentional ambiguity and noise patterns

Every case is tagged with a `gt_difficulty_archetype` (ground truth — a
model should never see this at input time) that controls how the LLM rendered
the narrative:

| Archetype | Share | What it does |
|---|---|---|
| `clear` | ~55% | Well-formed, complete ticket |
| `vague` | ~12% | Short, underspecified, missing detail a real agent would want |
| `customer_misdiagnosis` | ~12% | Customer confidently states an incorrect cause (`customer_asserted_cause`, sampled from a *different* root cause than the true one) in plain language, e.g. "we think this is a firewall problem" |
| `wrong_product_mentioned` | ~7% | Customer names a different, plausible product in the same product category than the one actually at fault (`product_reported_id` ≠ `gt_product_id`) |
| `multi_component_symptoms` | ~8% | Symptoms described could plausibly implicate either the true component or a second candidate component (`case_components.csv` relation=`candidate`) |
| `dependency_root_cause` | ~6% | The true root cause lives in an upstream/third-party dependency, but the customer has no way to know that and doesn't mention a vendor at all |

Additional, always-on sources of ambiguity (not archetype-gated):

- **Root cause is never a deterministic function of category or symptom.**
  Every subcategory maps to 2–4 plausible root causes (`issue_subcategory_root_causes.csv`);
  the same symptom (e.g. "timeout") legitimately appears under Performance,
  Networking, Integration/API, and Third-Party categories
  (`issue_subcategory_symptoms.csv` / `symptoms.csv` — no symptom is
  category-exclusive).
- **Ownership is frequently ambiguous.** Every one of the 126 subcategories
  has ≥2 candidate teams; `case_team_ownership.csv` records both the actual
  primary and (for ~60% of cases) a plausible secondary team.
- **Reported impact/scope can be wrong.** `reported_affected_users` is the
  true count times a random 0.5×–1.5× factor, so `reported_business_impact`
  and `gt_true_business_impact` sometimes land in different buckets even for
  `clear` archetype cases.
- **Similar cases, different causes.** `similar_cases.csv` pairs cases within
  the same subcategory, but each case's `gt_root_cause_id` was drawn
  independently — two near-identical-looking tickets can have different
  confirmed causes.

## Section 7 — Graph mapping (for a future Neo4j loader)

Not implemented in Phase 1 (`agent/neo4j_loader.py` is untouched and still
loads `data/raw/`), but every table here is shaped for a 1:1 node/relationship
mapping later:

```
(Customer)-[:RAISED]->(Case)
(Case)-[:REPORTED_PRODUCT]->(Product)      -- case_products.csv relation=reported
(Case)-[:CONFIRMED_PRODUCT]->(Product)     -- case_products.csv relation=confirmed
(Case)-[:HAS_COMPONENT]->(Component)       -- case_components.csv
(Case)-[:HAS_SYMPTOM]->(Symptom)
(Case)-[:CLASSIFIED_AS]->(IssueSubcategory)-[:BELONGS_TO]->(IssueCategory)
(Case)-[:CAUSED_BY]->(RootCause)-[:RESOLVED_BY]->(ResolutionType)
(Case)-[:OWNED_BY {role}]->(Team)
(Case)-[:REQUIRES_SKILL]->(Skill)
(Case)-[:ASSIGNED_TO {role}]->(Agent)
(Case)-[:REFERENCED]->(KnowledgeArticle)
(Case)-[:SIMILAR_TO {score}]-(Case)
(Agent)-[:HAS_SKILL {proficiency}]->(Skill)
(Agent)-[:MEMBER_OF]->(Team)
(Agent)-[:EXPERT_IN]->(Product|Component)
(Product)-[:HAS_COMPONENT]->(Component)-[:OWNED_BY {role}]->(Team)
(IssueSubcategory)-[:TYPICALLY_INVOLVES {weight}]->(Symptom|Component|Skill|Team|RootCause)
(KnowledgeArticle)-[:COVERS]->(Product|Component|IssueSubcategory|Symptom|RootCause|ResolutionType)
```

## Section 8 — Reproducibility

- Structural generation (`generate_structural.py`, `generate_cases.py`) uses
  `random.seed(42)` / `Faker.seed(42)` — re-running produces bit-identical
  ground truth given the same call order.
- Narrative text (`narratives.py`) is cached per-batch/per-item in
  `data/generators/.narrative_cache/*.json`, keyed by a hash of the exact
  prompt (model, temperature, reasoning effort, seed, message content).
  Re-running the pipeline replays cached text rather than re-calling the API;
  an interrupted run resumes from wherever the cache leaves off without
  re-spending tokens. Deleting the cache directory forces full regeneration.
- This build's actual Together AI spend: **$2.4659** (2,078 calls, 3.50M
  input / 4.13M output tokens) for the full 25,000-case + 900-article
  narrative pass, at `Qwen/Qwen3.8-Flash`, `reasoning_effort: "low"`.
